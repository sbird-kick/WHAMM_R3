whamm: real JS engine (QuickJS-ng v0.10.1, wasm32-wasip1) blocked on TWO whamm-side scaling limits; engine itself builds and is deterministic under the plain Wizard R3 oracle (9 events, byte-identical across runs; stdout deterministic).

(1) STACK OVERFLOW at default 8MB stack. script_gen emits the EC entry probe as one predicate `opidx == 0 && (fid == 5 || fid == 7 || ... )` with one OR-term per non-excluded function. QuickJS defines 1039 functions -> a 1044-term OR expression (~14.5 KB single line). whamm's recursive parse/lowering of that deeply-nested binary expr overflows the main-thread stack: "thread 'main' has overflowed its stack / fatal runtime error: stack overflow, aborting" (SIGABRT). Threshold is ~500 OR-terms (400 OK, 600 aborts). Minimal repro (2-function .wat + generated big-OR script, NO real engine needed) in ./js_whamm_or_overflow_repro/. Workaround `ulimit -s 65500` lets it parse -> confirms pure recursion-depth limit, i.e. a real whamm robustness bug (should not abort on a valid script; needs iterative lowering or a depth guard/larger stack).

(2) TOO SLOW even past (1). With the stack raised, `whamm instr` of a *minimal* base+eval build (899 fns, 396 KB) took 564 s (~9.4 min); a *trivial* `opidx==0` probe over the full 1039-fn build took 340 s (~5.7 min). Both are ~100x over the ~5s harness budget; the full R3 script would be worse. QuickJS's giant interpreter functions (JS_CallInternal etc.) make per-opcode instrumentation cost pathological. No amount of feature-stripping helps: JS_Eval alone pulls in ~900 functions, still far above the ~500 overflow threshold.

Conclusion: not a divergence and not weakenable. The whamm-based R3 pipeline cannot instrument a real single-file JS engine — file (1) as a whamm bug; (2) is an honest scalability limit. Artifacts: js_quickjs_r3.{c,js,wasm}, js_BUILD.txt (reproducible), js_whamm_or_overflow_repro/ (minimal bug repro).
